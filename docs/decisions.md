# Evex — Log de decisões técnicas (ADR)

> Histórico de **por que** as coisas foram feitas de um jeito e não de outro. Complementa [`roadmap.md`](roadmap.md) (que registra **onde estamos**). Toda decisão técnica não trivial — de qualquer agente ou sessão — entra aqui, na ordem em que foi tomada. Não editar/apagar entradas antigas para "corrigir": se uma decisão foi revista depois, registrar uma nova entrada apontando para a antiga (`Substitui: DEC-00X`).

## DEC-001 — Escopo do `eth_getLogs`: rede inteira, sem filtro de endereço
Data: 2026-08-21
Módulo: backend
Autor: sessão de análise inicial
Contexto: o poller precisa decidir se busca `eth_getLogs` só dos endereços monitorados (mais barato) ou da rede inteira, filtrando depois (como o código base da Anbima faz).
Decisão: escutar a rede inteira, sem filtro de endereço — igual ao código base.
Alternativas consideradas: filtrar por endereço monitorado (mais barato, mas contrato cadastrado depois perderia histórico até ser cadastrado, contrariando "nenhum evento é descartado").
Consequências: cursor de indexação é **global único** (não por contrato) — ver DEC-002. Custo de RPC maior em redes com muito tráfego; aceito por ora na PoC.

## DEC-002 — Cursor de indexação global único
Data: 2026-08-21
Módulo: backend
Autor: sessão de análise inicial
Contexto: decorre diretamente da DEC-001.
Decisão: 1 cursor global (`last_processed_block`), não 1 por contrato.
Consequências: simplifica a implementação do poller; se no futuro o escopo mudar para filtro por endereço, essa decisão precisa ser revista junto.

## DEC-003 — Só polling, sem WebSocket/subscription
Data: 2026-08-21
Módulo: backend
Autor: sessão de análise inicial
Contexto: Web3j suporta tanto `eth_getLogs` via polling quanto subscription via WebSocket (`ethLogFlowable`).
Decisão: só polling na PoC — reaproveita o padrão `PollWindow`/auto-shrink já validado no código base.
Alternativas consideradas: WebSocket (mais responsivo, mas adiciona complexidade de reconexão/gap de eventos perdidos durante desconexão).
Consequências: WebSocket fica como possível item pós-aprovação, não é dívida técnica da PoC — decisão consciente de escopo.

## DEC-004 — Webhooks são uma feature de notificação de saída, não uma opção de conexão com a rede
Data: 2026-08-21
Módulo: backend
Autor: sessão de análise inicial
Contexto: possível confusão entre "polling vs. WebSocket" (DEC-003, é sobre RPC de entrada, rede→indexer) e "webhooks" (doc de produto §4.6, é sobre notificação de saída, indexer→sistema externo via HTTP POST configurado pelo usuário).
Decisão: são módulos independentes. Pipeline de indexação usa só polling (DEC-003); webhooks são disparados depois que um evento é decodificado e bate numa config de usuário — implementados do zero (não existe nada equivalente no código base).
Consequências: nenhuma dependência entre as duas decisões; podem evoluir separadamente.

## DEC-006 — Schema management: `ddl-auto: update` como padrão + Flyway parcial quando necessário

## DEC-007 — Suporte a proxy upgradável: ABI versionada por faixa de blocos
Data: 2026-08-21
Módulo: backend
Autor: sessão de análise inicial
Contexto: os ABIs de referência da Anbima incluem `ERC1967Proxy`, sugerindo que contratos reais da BBChain usam padrão de proxy upgradável — o mesmo endereço pode trocar de implementação (e portanto de ABI) ao longo do tempo. O doc de produto original não cobria esse cenário.
Decisão: `contract_abis` suporta múltiplas linhas por endereço, cada uma com `valid_from_block`/`valid_to_block`. A decodificação resolve "qual ABI valia neste bloco", não "qual é a ABI deste endereço".
Alternativas consideradas: assumir 1 ABI ativa por endereço (mais simples, mas quebra a decodificação de histórico após um upgrade de proxy).
Consequências: cache em memória de ABI não pode ser `Map<contractAddress, Abi>` simples — precisa resolver por bloco (ver `../backend/docs/abi-strategy-design.md` seção 5).

## DEC-012 — Spec OpenAPI multi-arquivo granular, bundlada via Redocly CLI antes do openapi-generator
Data: 2026-08-22
Módulo: backend
Autor: sessão principal (execução da E1)
Contexto: usuário pediu que os arquivos da spec OpenAPI fossem bem granulares para manutenção/visibilidade, com um bundle final alimentando o `openapi-generator`. Perguntado sobre 3 estruturas possíveis (por camada, por recurso, granularidade máxima), o usuário descreveu sua própria estrutura preferida: pasta `swagger/` com uma `base/` que agrega tudo (contendo `components/` subdividido em `schemas/`, `requests/`, `responses/`, `param/query/`, `param/path/`, `enum/`), uma pasta `paths/`, e uma pasta `bundle/` pro artefato final.
Decisão: adotada a estrutura descrita pelo usuário, com um ajuste técnico necessário: cada arquivo em `paths/` representa **1 Path Item Object (1 URL literal)**, não 1 tag inteira — restrição do próprio mecanismo de `$ref` do OpenAPI (não dá pra referenciar 2 URLs diferentes com 1 só `$ref`). Bundle via **Redocly CLI** (`npx @redocly/cli bundle`, sucessor do `swagger-cli` descontinuado) numa task Gradle `bundleEvexApi` (`Exec`), rodando antes de `generateEvexApi`. Estrutura completa documentada em `backend/docs/openapi-first-workflow.md`.
Alternativas consideradas: apontar o `openapi-generator` direto pro `base.yaml` multi-arquivo sem bundle explícito (tecnicamente viável, o `swagger-parser` interno resolve `$ref` relativo) — descartado porque o usuário pediu explicitamente um artefato de bundle, e ter o contrato "resolvido" como arquivo único inspecionável tem valor por si só (revisão, outras ferramentas).
Consequências: **Node.js vira dependência de build** (antes só precisava JVM/Gradle) — `npx` roda via Node já instalado neste ambiente (v22.13.1), mas isso precisa estar documentado no setup do backend/CI. Cada novo endpoint exige pensar em qual arquivo de `paths/` ele pertence (1 por URL) e criar/reusar os componentes certos nas subpastas — mais arquivos que uma spec monolítica, compensado pela visibilidade pedida.

## DEC-013 — Schema de erro próprio (`ErrorResponse`), não o default do Spring Boot
Data: 2026-08-22
Módulo: backend
Autor: sessão principal (execução da E1)
Contexto: `openapi-first-workflow.md` já sinalizava esse ponto em aberto desde a análise do código base (o `.yaml` da Anbima não define schema de erro, depende do corpo default do Spring Boot).

## DEC-014 — `adapters/in`/`adapters/out` renomeados para `adapters/inbound`/`adapters/outbound`
Data: 2026-08-22
Módulo: backend
Autor: sessão principal (execução da E1)
Contexto: ao configurar `apiPackage`/`modelPackage` do `openapi-generator` para `br.com.bbchain.evex.indexer.adapters.in.api.generated`, notei que `in` é **palavra reservada obrigatória (hard keyword)** em Kotlin — usar como segmento de pacote exigiria escapar com backtick (`` adapters.`in`.api ``) em toda referência, algo frágil e não garantidamente bem suportado pelos templates de geração de código do openapi-generator. Essa estrutura já vinha sendo usada desde o scaffold de E0 (`adapters/in/`, `adapters/out/`) sem que esse problema tivesse sido percebido.
Decisão: renomear para `adapters/inbound` e `adapters/outbound` em todo o projeto (pastas físicas, `build.gradle.kts`, todos os `CLAUDE.md`, todos os docs técnicos, todos os agentes em `.claude/agents/`). `out` isoladamente não teria esse problema (é *soft keyword*, só reservado em contexto de variância `<out T>`, usável como identificador normal) — mas troquei os dois para manter simetria e nomes mais descritivos.
Consequências: nenhuma — troca puramente de nome, sem impacto de design. Fica registrado para não reintroduzir `adapters/in` por engano em algum doc futuro.

## DEC-016 — Validação de `@PathVariable`/`@RequestParam` lança `ConstraintViolationException`, não `HandlerMethodValidationException`
Data: 2026-08-22
Módulo: backend
Autor: sessão principal (execução da E1)
Contexto: ao implementar o `ErrorResponse` padrão (DEC-013) para `GET /v1/contracts/{address}` com endereço malformado, o handler para `HandlerMethodValidationException` (exceção "nativa" do Spring MVC 6.1+ para validação de parâmetro de método, esperada por documentação/experiência com versões anteriores do Spring) não foi disparado — o corpo de erro continuava sendo o formato default do Spring Boot, não o `ApiError` do spec.
Decisão: nesta combinação (Spring Boot 4.1.1 / Spring Framework 7.0.9), a exceção real é `jakarta.validation.ConstraintViolationException` (Bean Validation "crua"). Adicionado `@ExceptionHandler(ConstraintViolationException::class)` no `ApiExceptionHandler`, mantendo também o handler de `HandlerMethodValidationException` como fallback (não custa, cobre os dois casos caso o comportamento mude entre versões do Spring).
Consequências: qualquer novo endpoint com `@PathVariable`/`@RequestParam` validado por Bean Validation já está coberto pelo `ApiExceptionHandler` existente — não precisa de handler novo por recurso. Vale reconfirmar esse comportamento se a versão do Spring Boot for atualizada no futuro.

## DEC-017 — `*/` literal dentro do KDoc de `resolveNpx()` fechava o comentário cedo demais, apagando `bundleEvexApi`/`generateEvexApi` do build silenciosamente
Data: 2026-08-22
Módulo: backend
Autor: sessão principal (investigação pré-E2)
Contexto: depois de editar `build.gradle.kts` para adicionar `resolveNpx()` (resolver `npx` sem depender do PATH herdado — nvm carregado só em `~/.bashrc`, invisível a processos não-interativos como o Gradle daemon disparado pelo IntelliJ no Windows sincronizando o projeto via WSL), as tasks `bundleEvexApi`/`generateEvexApi` sumiram de `./gradlew tasks --all` e `./gradlew generateEvexApi` passou a falhar com "Task not found" — sem nenhum erro de compilação, `BUILD SUCCESSFUL` em todo o resto. A hipótese inicial (tasks só apareciam sob outro cabeçalho de grupo, "Openapi tasks" vs. o grupo do próprio plugin) foi checada e descartada: as tasks realmente não existiam em lugar nenhum do output. A suspeita seguinte foi antivírus interferindo no filesystem WSL — também descartada.
Decisão: causa raiz isolada por bisseção binária inserindo `println` em pontos progressivos do script até localizar exatamente onde a execução parava (sem exceção, sem log — simplesmente as declarações depois de um certo ponto nunca eram alcançadas). O KDoc de `resolveNpx()` continha, como texto ilustrativo, o caminho `~/.nvm/versions/node/*/bin/npx` — a subsequência `*/` dentro desse caminho fecha o comentário de bloco (`/** ... */`) prematuramente no meio da frase, porque Kotlin não tem mecanismo de escape para `*/` dentro de comentários. Todo o texto depois disso (resto do KDoc, incluindo o `*/` "real" pretendido como fechamento) passa a ser interpretado como código, produzindo tokens que o parser tolera de forma degenerada nesse caso específico — sem lançar erro de compilação visível, mas resultando num estado onde as declarações de `bundleEvexApi`/`generateEvexApi` mais adiante no arquivo simplesmente não são processadas. Fix: reescrita a frase do KDoc para descrever o mesmo fallback (`~/.nvm/versions/node/<versão>/bin/`) sem usar o glob `*/` literal — nenhuma mudança de comportamento em `resolveNpx()` em si.
Alternativas consideradas: nenhuma — é um bug de conteúdo do comentário, não de design; a única correção é não ter `*/` literal dentro de um bloco `/** */`.
Consequências: **regra geral para qualquer comentário de bloco (`/* */` ou `/** */`) neste projeto (e em qualquer `.kt`/`.kts`): nunca escrever `*/` literal no meio do texto** — caminhos de glob (`dir/*/subdir`), padrões regex ou qualquer texto ilustrativo que contenha essa sequência precisam ser reescritos (ex.: `<versão>` no lugar do `*`) ou movidos para comentário de linha (`//`, que não sofre desse problema). Validado: `./gradlew tasks --all` mostra as duas tasks sob "Openapi tasks"; `./gradlew build` verde de novo (bundle → generate → compile → jar → build, 7 tasks executadas).

## DEC-018 — `MonitoredContractEntity` implementa `Persistable<UUID>` com `id` privado + `getId()` explícito (não `override val id`)
Data: 2026-08-22
Módulo: backend
Autor: sessão principal (execução da E2)
Contexto: `MonitoredContract.id` é um `UUID` gerado em `application` (`UUID.randomUUID()`), não pelo banco. O `isNew()` default do Spring Data JPA (`SimpleJpaRepository`) é baseado em `id == null` — como o `id` já vem preenchido antes do primeiro `save()`, todo insert seria tratado como já-existente e viraria um `SELECT` + `MERGE`/`UPDATE` silencioso (sem erro, mas sem `INSERT` real) em vez de criar a linha. Fix padrão do Spring Data para esse cenário é a entidade implementar `org.springframework.data.domain.Persistable<ID>`, com uma flag transiente controlando `isNew()` explicitamente.
Decisão: `MonitoredContractEntity` implementa `Persistable<UUID>` com `@Id private val id: UUID` (não `override val id: UUID` pública) e um `override fun getId(): UUID = id` escrito à mão. A primeira tentativa foi `override val id: UUID` direto na constructor (assumindo que a propriedade Kotlin satisfaria o método Java `getId()` do jeito que satisfaz interfaces *Kotlin*) — não compilou (`'id' overrides nothing` + `Class ... does not implement abstract member fun getId()`): esse mapeamento automático propriedade→getter só vale para interfaces definidas em Kotlin (ou um punhado de tipos do stdlib com suporte especial), não para uma interface Java qualquer como `Persistable`. A flag `new: Boolean` (também `@Transient`) é setada pelo `JpaMonitoredContractAdapter` via `existsById(contract.id)` antes de montar a entidade para `save()`.
Alternativas consideradas: (1) deixar o banco gerar o `id` (sequence/identity) — rejeitado, já é padrão do projeto gerar `UUID` em `application` (mencionado no próprio plano aprovado desta etapa, reaproveitado de E1); (2) `override val id: UUID` público — não compila contra uma interface Java pelo motivo acima; se fosse tentado sem o `getId()` explícito, o erro só aparece em tempo de compilação, não em runtime, então não é um risco silencioso, mas custou uma iteração.
Consequências: **regra para qualquer entidade JPA futura do projeto com `id` gerado fora do banco (padrão já em uso desde E1 para `MonitoredContract`)**: implementar `Persistable<ID>` com `id` **privado** + `override fun getId()` explícito, nunca `override val id` tentando satisfazer a interface Java implicitamente. `JpaMonitoredContractAdapter.toDomain()` precisa chamar `entity.getId()` (não `entity.id`) por causa da visibilidade privada — documentado como comentário no próprio `MonitoredContractEntity.kt`.

## DEC-019 — Spring Boot 4 moveu `@DataJpaTest`/`@AutoConfigureMockMvc`/`@AutoConfigureTestDatabase` para artefatos Maven por tecnologia
Data: 2026-08-22
Módulo: backend
Autor: sessão principal (execução da E2)
Contexto: ao escrever os primeiros testes de integração do projeto (`JpaMonitoredContractAdapterTest`, `ContractsApiTest`), `import org.springframework.boot.test.autoconfigure.orm.jpa.DataJpaTest` / `...web.servlet.AutoConfigureMockMvc` / `...jdbc.AutoConfigureTestDatabase` não resolveram — `Unresolved reference`, mesmo com `spring-boot-starter-test` (que declara `spring-boot-test-autoconfigure` como dependência transitiva) já presente. Inspecionado o jar de `spring-boot-test-autoconfigure:4.1.1` baixado: só ~28KB, contendo unicamente os subpacotes `jdbc` (parcial, só `AutoConfigureDataSourceInitialization`) e `json` — nada de `orm/jpa`, `web/servlet`, `data/jpa`.
Decisão: Spring Boot 4 replicou, para os test slices, a mesma modularização por tecnologia que já existe no autoconfigure principal (`spring-boot-webmvc`, `spring-boot-jpa`, `spring-boot-data-jpa`, etc. — visível nas dependências do próprio `spring-boot-starter-web`/`spring-boot-starter-data-jpa`). Descoberto por resolução exploratória de coordenadas candidatas via um projeto Gradle descartável: `AutoConfigureMockMvc`/`WebMvcTest` → artefato `org.springframework.boot:spring-boot-webmvc-test`, pacote `org.springframework.boot.webmvc.test.autoconfigure`; `DataJpaTest` → `org.springframework.boot:spring-boot-data-jpa-test`, pacote `org.springframework.boot.data.jpa.test.autoconfigure`; `AutoConfigureTestDatabase` → `org.springframework.boot:spring-boot-jdbc-test`, pacote `org.springframework.boot.jdbc.test.autoconfigure`. Adicionadas as 3 como `testImplementation` em `build.gradle.kts`, sem versão explícita (resolvida pelo BOM `spring-boot-dependencies` via `io.spring.dependency-management`, igual ao resto do projeto).
Alternativas consideradas: nenhuma — não há como usar essas anotações sem declarar os módulos corretos; a única "alternativa" seria não usar `@DataJpaTest`/`@AutoConfigureMockMvc` (ex.: `@SpringBootTest` completo para tudo), rejeitada por ser mais pesado que necessário para o teste de repositório.

## DEC-024 — `Web3jBlockchainClient.isRangeError`: heurística não validada contra nó real; `src/test/resources/application.yml` shadowing descoberto na E4
Data: 2026-08-22
Módulo: backend
Autor: agente `blockchain-integration` (execução da E4)
Contexto: dois achados não previstos no plano da E4, ambos vale registrar em detalhe.

**(1) Heurística de detecção de erro de range do `eth_getLogs`.** `RpcRangeException` precisa ser distinguida de qualquer outro erro do nó (que não deve disparar o auto-shrink) — mas sem Besu/Hardhat real disponível (E12/DEC-010), não há como observar a mensagem/código de erro reais que a rede vai devolver quando um range é grande demais. Decisão: `Web3jBlockchainClient.isRangeError()` combina (a) o código JSON-RPC `-32005` ("limit exceeded", convenção usada por alguns provedores/clientes para range grande demais) com (b) um conjunto de palavras-chave conhecidas de mensagens de erro de implementações Ethereum/Besu documentadas publicamente (geth: "query returned more than N results"; Besu: variações de "block range"/"exceeds the range limit"/"too large"), comparadas case-insensitive contra `error.message`. Nenhuma dessas mensagens foi observada contra um nó real — é uma lista de melhor esforço.
Alternativas consideradas: (a) tratar **qualquer** erro do nó como candidato a range error — rejeitada, violaria a regra "erro de transporte não dispara shrink" (`ingestion-pipeline-reference.md` §2), arriscando shrink infinito/mascarar bugs reais de RPC; (b) não implementar detecção nenhuma até ter um nó real — rejeitada, deixaria o poller sem cobertura de teste de auto-shrink nesta etapa, contrariando o critério de aceite explícito do roadmap.
Consequências: **pendência explícita para quando E12 destravar** — rodar o poller contra Besu real com um range deliberadamente grande demais, capturar a mensagem/código de erro exatos, e ajustar `RANGE_ERROR_CODE`/`RANGE_ERROR_KEYWORDS` de acordo (upgrade de heurística pra fato observado). Os testes (`Web3jBlockchainClientTest`) cobrem a lógica de decisão em si (dado um `Response.Error` fabricado, classifica certo/errado), não a heurística contra o nó de verdade.

**(2) `src/test/resources/application.yml` shadowing `src/main/resources/application.yml` no classpath de teste.** Ao seguir o plano literalmente (criar `src/test/resources/application.yml` com `indexer.blockchain.polling-enabled: false`), 43 dos 104 testes do projeto — inclusive testes de entidades sem nenhuma relação com E4 (`monitored_contracts`, `contract_abis`) — passaram a falhar com `relation "X" does not exist`, e todo teste `@SpringBootTest` falhou já no carregamento do contexto. Causa raiz: no classpath efetivo de teste do Gradle, `build/resources/test` é resolvido **antes** de `build/resources/main` — então `getResource("classpath:application.yml")` do Spring Boot encontra só o arquivo de teste, e ele **substitui inteiramente** (não mescla com) o `application.yml` principal. `ddl-auto: update`, config de batching, Flyway, tudo o que só existia em `src/main/resources/application.yml` desaparecia silenciosamente pros testes — sem erro, sem warning, só "tabela não existe" like Hibernate nunca tivesse rodado nenhuma DDL. Diagnosticado comparando `ddl-auto=update` (zero DDL executado, nenhuma linha de log de `create table`) vs. `ddl-auto=create-drop` (funcionava, criava e derrubava as 4 tabelas do zero — o que por acaso mascararia o mesmo bug se create-drop fosse o padrão do projeto).
Decisão: **nunca criar `src/test/resources/application.yml` neste projeto.** Overrides de propriedade para testes vão via `@DynamicPropertySource` em `AbstractIntegrationTest` (mesmo mecanismo já usado pro datasource dinâmico do Testcontainers desde E2) ou `@TestPropertySource(properties = [...])` pontual por classe de teste — nunca um arquivo de config paralelo com o mesmo nome do principal.
Alternativas consideradas: `spring.config.import`/`spring.profiles.active` apontando pra um `application-test.yml` com nome diferente (funcionaria, evita o shadowing por ter nome distinto) — descartada em favor de `@DynamicPropertySource`, que já é o padrão estabelecido no projeto desde E2 e não introduz um segundo arquivo de config pra manter sincronizado com o principal.
Consequências: regra geral pro projeto — qualquer property override específico de teste (não só `indexer.blockchain.polling-enabled`) deve usar `@DynamicPropertySource`/`@TestPropertySource`, nunca um `application.yml`/`application.properties` em `src/test/resources`. Vale revisar se algum agente futuro tentar essa abordagem de novo sem saber deste achado.

## DEC-026 — Teste `@Async` real exige abrir mão de `@Transactional`; primeira classe de teste do projeto sem rollback automático, precisa de limpeza explícita
Data: 2026-08-22
Módulo: backend
Autor: agente `blockchain-integration` (execução da E5)
Contexto: `RedecodeAcceptanceTest` (teste de ponta a ponta do critério de aceite da E5, com `@Async`/`@EnableAsync` funcionando de verdade, via Awaitility) precisa que o `RedecodeRunner` — rodando numa thread separada do pool do `@Async` — enxergue os dados de setup (contrato, ABI, eventos raw) inseridos pelo corpo do teste. Consequências: **regra geral pro projeto** — qualquer teste futuro que precise de `@Async`/`@Scheduled` rodando de fato (não mockado) não pode usar `@Transactional`, e precisa limpar seus próprios dados explicitamente (endereços/IDs aleatórios rastreados + `@AfterEach`) pra não contaminar o resto da suíte no container Postgres singleton compartilhado. `RedecodeAcceptanceTest` é o primeiro precedente deste padrão — referenciar esta decisão se E7/E8 (que também mexem com processamento assíncrono/agendado) precisarem de testes de ponta a ponta equivalentes. `./gradlew clean build`/`./gradlew test --rerun` reconfirmados verdes 3x seguidas (130/130) depois do fix, sem sinal de flakiness remanescente.

## DEC-027 — Revisão da E5: flakiness real em `RedecodeAcceptanceTest` (trigger automático de redecode descartado silenciosamente por corrida com `tryStart`), fix aplicado; gap de cobertura do critério de parada do loop, fix aplicado
Data: 2026-08-22
Módulo: backend
Autor: agente `reviewer` (revisão da E5)
Contexto: dois achados durante a revisão, ambos corrigidos na hora (baixo risco, alto valor).

**(1) Flakiness real pega por `./gradlew clean build --rerun`.** `RedecodeOrchestrator.tryStart()` é por design "1 execução por vez, não enfileira, não acumula" (`ingestion-pipeline-reference.md` §4, replicado fielmente do código base) — se `running` já é `true`, a chamada simplesmente retorna `false` sem agendar nada. Isso é correto e documentado no próprio KDoc da classe. Só que `RedecodeAcceptanceTest > redecode triggered manually by topic0 affects multiple contracts` chama `registerAbi(addressA)` e `registerAbi(addressB)` em sequência (cada `registerAbi` dispara sozinho uma reindexação automática via `AbiRegistrationService.register()` → `tryStart`), e logo em seguida um `POST /v1/redecode` manual (outro `tryStart`) — sem esperar a reindexação automática anterior terminar. Como o `@Async` roda em thread separada e o tempo entre "response HTTP do `registerAbi`" e "a reindexação automática de fato termina (`onFinished()`)" não é determinístico, o `tryStart` seguinte (de outro `registerAbi`, ou do `POST /v1/redecode` manual do teste) podia cair no meio da execução anterior ainda em andamento e ser descartado — silenciosamente, sem erro, sem 4xx (a resposta HTTP é sempre `202` com o `status()` real, mesmo quando `tryStart` retornou `false`). Reproduzido de forma determinística: `./gradlew clean build --rerun` (1ª rodada) verde, `./gradlew clean build --rerun` (2ª rodada, JIT/caches "quentes" diferentes) falhou exatamente nesse teste, por timeout do `Awaitility` (10s) — o evento nunca foi decodificado porque o `POST /v1/redecode` manual não tinha, de fato, disparado nada.

Se alguém trocasse `result.decodedCount == 0` por `result.processedCount == 0`/`candidates.isEmpty()` no futuro, nenhum teste do projeto teria detectado a regressão.
Decisão: criado `RedecodeRunnerTest` (novo, `application/redecode/`) com 3 testes: (1) o cenário central — 1º lote com mistura decodificável/não-decodificável (`processedCount=5, decodedCount=3`), 2º lote só com os remanescentes permanentemente não-decodificáveis (`processedCount=2, decodedCount=0`) — prova que o loop para depois do 2º lote (não continua pra um 3º, que o mock faz falhar explicitamente em vez de deixar rodar pra sempre, pra não travar a suíte em caso de regressão futura); (2) 1 lote já com `decodedCount=0` para quando de imediato; (3) `onFinished()` chamado mesmo quando `processBatch` lança exceção.
Consequências: 133 testes no total do projeto (130 de E1-E5 relatados pelo agente + 3 novos deste `RedecodeRunnerTest`). `./gradlew clean build` reconfirmado verde depois dos dois fixes.

## DEC-033 — `@Modifying` nativa com `ON CONFLICT` não invalida o 1º-level cache do Hibernate — precisa de `clearAutomatically = true`
Data: 2026-08-23
Módulo: backend
Autor: agente `kotlin-backend-dev` (execução da E7)
Contexto: `JpaAssetBalanceAdapterTest` (novo, `@DataJpaTest`+Testcontainers) tinha um cenário de `snapshotAll` idempotente: rodar o job 2x na mesma transação de teste (aplicar um delta extra entre as 2 rodadas, esperando o snapshot da 2ª rodada refletir o saldo somado). A 1ª rodada passava, a 2ª sempre devolvia o valor da 1ª — como se o `UPDATE` do `ON CONFLICT DO UPDATE` da 2ª chamada nunca tivesse acontecido, mesmo a query em si rodando sem erro (confirmado via log `Hibernate:`). Causa raiz: `upsertDelta`/`snapshotAll` são `@Query(nativeQuery = true)` — SQL puro executado direto pelo driver JDBC, **sem passar pelo gerenciamento de entidades do Hibernate**. A 1ª chamada a `searchHistory()` (via `Specification`/Criteria, JPQL) já tinha carregado a linha de `asset_balance_snapshots` correspondente no 1º-level cache (persistence context) da transação do teste, indexada pelo `id`. A 2ª chamada nativa atualiza a linha **no banco**, mas o Hibernate não sabe disso — a próxima leitura via `Specification` pro mesmo `id` devolve o objeto **já carregado em memória** (identity map do Hibernate: "se já tenho uma entidade gerenciada com este id nesta sessão, devolvo ela, não releio do banco"), com os valores antigos.
Decisão: `@Modifying(clearAutomatically = true)` nos 2 métodos nativos de `AssetBalanceJpaRepository` (`upsertDelta`/`snapshotAll`) — força o Spring Data a chamar `EntityManager.clear()` logo depois de executar a query modificadora, descartando todo o persistence context da transação corrente. Qualquer leitura seguinte (mesma transação) bate no banco de novo, sem risco de servir um objeto desatualizado. Achado real de teste de integração contra Postgres real, não hipotético — sem esse fix, `JpaAssetBalanceAdapterTest > snapshotAll consolidates current balances into today's snapshot, idempotent for the same day` falhava de forma determinística.
Alternativas consideradas: (a) `entityManager.refresh()` manual no adapter depois de cada chamada nativa — mais cirúrgico (só invalida a entidade específica, não o persistence context inteiro), mas exigiria injetar `EntityManager` direto no adapter (rompendo a fronteira "adapter só conhece o `JpaRepository`", padrão do resto do projeto) só pra esse caso; `clearAutomatically` é a solução idiomática do Spring Data pra exatamente este cenário; (b) não usar `Specification`/JPQL pra ler `asset_balances`/`asset_balance_snapshots`, só SQL nativo em todo lugar — inconsistente com o resto do projeto (toda leitura via `Specification` dinâmica, `JpaBlockchainEventAdapter` inclusive) e perderia a composição de filtros opcionais que `Specification.allOf(listOfNotNull(...))` já dá de graça.
Consequências: **regra geral pro projeto** — qualquer `@Query(nativeQuery = true)` futuro que seja `@Modifying` e escreva numa tabela também lida via `Specification`/JPQL na mesma transação precisa de `clearAutomatically = true` (ou `refresh()` manual), senão leituras subsequentes na mesma transação podem servir dado desatualizado do 1º-level cache. Não afeta transações/requisições diferentes (cada uma tem seu próprio persistence context) — só importa dentro da mesma transação/sessão Hibernate, exatamente o cenário do teste de integração que pegou isso.

## DEC-044 — Revisão da E8.1: janela real (não hipotética) entre Tomcat aceitar conexões e Flyway/`AbiCache` rodarem — ambos em `ApplicationReadyEvent`, port já aberto antes disso
Data: 2026-08-23
Módulo: backend
Autor: agente `reviewer` (revisão da E8.1)
Contexto: item 2 do escopo de revisão pedia confirmar que não existe corrida entre o boot terminar e o índice único parcial (DEC-022/DEC-041) ainda não existir. Investigado via `bootRun` real contra o Postgres do `docker-compose.yml`, log com timestamp em milissegundos: `Tomcat started on port 8091` às `13:33:34.031`, `AbiCache: ... warm-up` às `13:33:34.140`, `FlywayExecutor`/`.migrate()` (via `PostSchemaFlywayMigrator`) começando às `13:33:34.147`. Ou seja, **o Tomcat já está de fato aceitando conexões TCP reais ~110ms antes** de `AbiCache` estar quente e do Flyway ter rodado — não é hipotético, é o comportamento observado num boot real. Causa: o `WebServerStartStopLifecycle` (bean `SmartLifecycle` que efetivamente abre o socket do Tomcat pra aceitar tráfego — antes disso o conector existe mas está "removido"/pausado, ver `TomcatWebServer.initialize()`/`start()`) roda durante `finishRefresh()` do `AbstractApplicationContext.refresh()`, **antes** de `ApplicationReadyEvent` ser publicado (que só acontece depois de `callRunners()`, já fora do `refresh()`). Alternativas consideradas (não aplicadas, registradas para se a equipe decidir fechar essa janela numa etapa futura de hardening — E11): (a) trocar `@EventListener(ApplicationReadyEvent::class)` por `SmartInitializingSingleton.afterSingletonsInstantiated()` em `PostSchemaFlywayMigrator` — esse callback roda ao final de `finishBeanFactoryInitialization()`, que termina **antes** de `finishRefresh()` (onde o `WebServerStartStopLifecycle` abre o socket), e a essa altura o schema do Hibernate já existe (a `EntityManagerFactory` já é um singleton totalmente inicializado) — fecharia a janela por completo sem mudar a ordem Flyway↔Hibernate já decidida em DEC-041, só adiantando o `.migrate()` pra antes do Tomcat abrir o socket em vez de depois. Não aplicada agora por prudência (mudança de mecanismo de lifecycle do Spring, vale validar com mais tempo/teste dedicado do que uma revisão permite) e porque o risco medido é baixo o bastante pra uma PoC; (b) gate de readiness (`/actuator/health` só `UP` depois do Flyway) combinado com um proxy/orquestrador que só rotea tráfego depois disso — fora de escopo da PoC (não há tal orquestrador na frente do Evex hoje).
Consequências: pendência explícita para E11 (hardening cross-cutting) ou para quando o Evex ganhar um orquestrador de deploy real na frente (health-gated rollout) — nesse ponto vale reavaliar aplicando a alternativa (a) acima. Não bloqueia a E8.1: o índice existe e funciona corretamente em qualquer instante após o boot terminar de fato (`ApplicationReadyEvent`), e a fatia de risco (poucos ms, endpoint administrativo de baixa frequência, PoC sem carga concorrente real) foi considerada aceitável para fechar a etapa.

## DEC-049 — `WarnLogDeduper`: dedupe de log `WARN` por chave, atualizando o carimbo só quando de fato loga (não a cada chamada)

Módulo: backend

## DEC-057 — 3 bugs reais encontrados no `BlockscoutClient`/fluxo de verificação, só visíveis contra Blockscout de verdade; todos corrigidos
Data: 2026-08-27
Módulo: backend
Autor: sessão principal (continuação da DEC-056, a pedido do usuário)
Contexto: com o Blockscout real (v11.2.8) no ar (DEC-056), o usuário sugeriu não depender do `rocketh-verify` (que fala API errada) e chamar a API v2 real de verificação diretamente. Isso destravou testar de ponta a ponta os 3 endpoints que o `BlockscoutClient` consome — e os 3 caminhos restantes (discovery, ABI via Blockscout, verificação) revelaram bugs reais no código de produção do Evex, não só do ambiente de teste. Nenhum desses bugs tinha como ser pego antes: os testes existentes (`BlockscoutClientTest`) usavam `MockRestServiceServer` com formato de resposta "best-effort" (documentado explicitamente no KDoc da classe como pendente de confirmação — nunca houve instância real disponível até esta sessão).
Achados e correções:
1. **`listVerifiedContracts()` usava `GET /api/v2/smart-contracts?filter=verified`** — nessa versão do Blockscout, `filter` é um enum de *linguagem* (solidity/vyper/yul), não de status de verificação; `filter=verified` é valor inválido (422 contra instância real). `GET /api/v2/smart-contracts` sem nenhum filtro já retorna só contratos verificados por padrão (a própria doc do endpoint diz "List verified smart contracts"). Corrigido removendo o query param.

Consequências: nenhuma mudança de comportamento visual pretendida — só de onde os valores de estilo são declarados (sempre `sx` a partir de agora pro projeto, já que a v9 não deixa escolha). Achado relacionado, sinalizado e não corrigido (fora do escopo deste agente): `decodedParameters` é serializado pelo Jackson padrão do backend sem customização pra `BigInteger` (confirmado por `grep` em `backend/src/main/kotlin` — nenhum serializer/`@JsonFormat` customizado) — valores grandes (`uint256` de token, por exemplo) viram literal numérico JSON e o `JSON.parse` do axios os transforma em `number` do JS com perda de precisão silenciosa acima de `Number.MAX_SAFE_INTEGER` (2^53). Não é regressão desta etapa (já valia antes) nem corrigível só no frontend — sinalizado pra avaliação futura do contrato/serialização (ex.: `AssetBalance.balance` já é `string` decimal por esse mesmo motivo, `decodedParameters` numéricos poderiam seguir o mesmo padrão).

## DEC-063 — `DecodedParamValue` (E13): o ramo de "string só de dígitos" não protege contra o que o comentário diz proteger; encaminhado como achado não-bloqueante, não corrigido nesta revisão
Data: 2026-08-28
Módulo: frontend
Autor: `reviewer` (revisão da E13, a pedido da sessão principal)
Contexto: revisando `DecodedParamValue.tsx` (E13/DEC-062) contra o backend real (`AbiDecodingAdapter.formatValue`, `backend/src/main/kotlin/.../adapters/outbound/abi/AbiDecodingAdapter.kt`), o componente tem um ramo dedicado a `string` composta só de dígitos, que aplica separador de milhar sem passar por `Number()`/`parseInt` — o comentário do código (e a DEC-062) justificam esse ramo como proteção contra `uint256`/`int256` que excedem `Number.MAX_SAFE_INTEGER`. Investigação de como `decodedParameters` de fato chega ao frontend: `BigInteger` (produzido pelo `formatValue` do backend pra tipos numéricos Solidity) é serializado pelo Jackson padrão (sem customização, confirmado por `grep` — mesmo achado já sinalizado na DEC-062) como **literal numérico JSON não-quotado**, não como string. O axios usa `JSON.parse` padrão (nenhuma customização em `src/api/base.ts`/`configuration.ts`), que converte esse literal direto em `number` do JS — com a perda de precisão (se houver) já consumada nesse ponto, antes de `DecodedParamValue` sequer rodar. Ou seja: um `uint256` grande nunca chega ao componente como `string`; chega como `number` já impreciso, caindo no ramo `typeof value === 'number'` (que só reformata o valor já perdido, não previne nada).
Decisão: registrar o achado sem corrigir nesta revisão — não é violação de regra do projeto (não quebra build/lint/typecheck, não é `useEffect`/HTTP manual/`any`), é um comentário/racional desalinhado com o comportamento real medido, prioridade baixa. Consequência prática observada: o ramo `DIGITS_PATTERN` (string só de dígitos) hoje só é alcançado por um parâmetro Solidity `string`/`bytes` cujo **valor decodificado em si** seja composto só de dígitos (ex.: um ID/código de referência de negócio guardado como `string` num evento, não um `uint`) — nesse caso, o componente aplica agrupamento de milhar (`1.234.567`) a um valor que semanticamente não é uma quantidade, potencialmente confundindo o usuário da UI.
Alternativas consideradas: (1) remover o ramo `DIGITS_PATTERN` e deixar cair no `string` genérico (mostra o valor cru) — mais simples, evita a formatação enganosa, mas perde a intenção original (nenhuma perda real, já que a intenção nunca foi cumprida na prática); (2) resolver na raiz, mudando a serialização do backend pra `decodedParameters` numéricos grandes virarem `string` decimal (mesmo padrão já usado em `AssetBalance.balance`) — aí sim o ramo `DIGITS_PATTERN` passaria a proteger o caso real de `uint256`, mas ganharia o problema inverso (não teria como distinguir, só pelo `typeof`, entre um `uint256` serializado como string e um parâmetro `string` Solidity que também é só dígitos — ambiguidade que só um contrato mais rico, tipo `{ name, type, value }`, resolveria de vez, já sinalizado como possível item futuro na DEC-062). Nenhuma das duas implementada nesta revisão — fica como item de follow-up de uma etapa futura que toque `decodedParameters`/serialização numérica (mesmo grupo do achado já aberto na DEC-062).
Consequências: nenhuma mudança de código nesta revisão. Documentado aqui pra não ser redescoberto do zero — qualquer trabalho futuro em `decodedParameters` (serialização de `BigInteger` como string, ou schema com tipo por parâmetro) deve revisitar este achado junto do da DEC-062, já que resolver um sem o outro não fecha o problema por completo (ambiguidade `string` vs. `uint` serializado como string).
